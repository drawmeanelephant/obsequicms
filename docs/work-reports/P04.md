# P04 work report: Site Readiness workspace

Status: complete. Branch `m0-prototype`. Depends on P02.

## What was built

`apps/web/src/features/readiness/**` (owned by this packet):

- `ReadinessPage.tsx` — workspace composition: loading/error/ready
  phases, category groups with counts, an attention filter
  (SegmentedControl), item rows with honest badges, and the detail panel.
  Failed requests render an error banner with working retry; no fallback
  data and no fabricated results.
- `useReadiness.ts` — data hook through the injected client.
- `staleness.ts` — pure staleness derivation: a complete observation is
  stale when its subject names a different source revision or release
  than displayed; generated artifacts compare source revisions;
  deployment records compare releases (including "none displayed").
  Time-based expiration is deliberately not invented.
- `attention.ts` — pure needs-attention rules: not configured, check
  error, failed or needs_review verdicts, unchecked-but-expected items
  (generated, deployed, or configured), and any stale evidence.
- `explanations.ts` — per-key purpose and applicability copy with the
  required honest boundaries: robots rules are cooperation and never
  privacy; analytics is optional and not a ranking requirement; llms.txt
  is an emerging proposal with no adoption claim; security.txt differs
  from a human-readable security page. No `cyborgs.txt`-style invented
  checks exist anywhere.
- `ItemDetail.tsx` — detail panel: purpose, applicability, configuration,
  generated artifact (with evidence ID and staleness), deployment (with
  evidence ID and staleness), last observation (verdict, method,
  observedAt, subject, evidence ID, stale banner with reason), and the
  next action. Activating an action explains "The backend is not
  connected in this prototype … changed nothing and ran no check" via a
  live region — no click ever becomes a fake check.

## Acceptance evidence (packet list)

- Generated-only data is not labeled deployed or verified: the sitemap
  detail states "Generated artifacts are not a deployment" and no verdict
  is fabricated (component + e2e).
- Older passed evidence is visibly stale for the displayed release: the
  canonical item shows an "Observation: stale" badge and the detail panel
  names both releases (component + e2e + logic tests).
- Missing evidence cannot produce a passing check: `not_checked` renders
  "An absent check is not a pass…", and verdicts only ever render from
  complete observations that structurally carry evidence IDs.
- Failures (social preview), manual review (image alt), not-applicable
  (llms, explicitly "different from unknown"), provider errors
  (analytics), and request errors remain distinct (component tests).
- Item detail and filters work with a keyboard at desktop and 390 CSS
  pixels (e2e; items are real buttons with visible focus).
- The six standard checks pass.

## Known gaps

- No readiness checker exists behind the UI (per contract, the prototype
  has no checker registry); observations are the synthetic demo records.
- Historical observation timelines arrive with scheduled checks in a
  later milestone; only the latest observation is displayed.
- `running` observations render from fixture data only; the demo client
  cannot start jobs.
