# P01 work report: shared contracts and demo data

Status: complete. Branch `m0-prototype`. Depends on P00.

## What was built

### `packages/contracts` (owned by this packet)

- `src/ids.ts` — branded opaque identifiers (`SourceRevision`, `JobId`,
  `ReleaseId`, `EvidenceId`, `EntityId`, `SourcePath`, `FileHash`), the UTC
  ISO 8601 timestamp schema, and the 8 MiB UTF-8 source-byte limit.
  `SourcePath` validation accepts only regular Markdown paths below
  `content/` and rejects traversal, backslashes, empty segments, and
  control characters.
- `src/errors.ts` — `ApiError` (`code`, `message`, nullable `requestId`),
  the seven error codes, the `ErrorResponse` schema, and `isApiError`.
- `src/pages.ts` — `PageSummary` (trunk⇔null parent / satellite⇔parent
  refinement), `DependencyEndpoint` (page|source discriminated union),
  `Dependency` (`parent` | `include` | `reference`), `Problem`, and
  `PageIndex` with the four explicit state variants enforced by
  refinements: `current` requires `graphRevision === sourceRevision`;
  `stale` requires a non-null differing revision; `unavailable` and
  `unsupported` require `graphRevision` null and empty `pages` and
  `dependencies`.
- `src/jobs.ts` — `SourceBuffer` and `SaveSourceRequest` (8 MiB limit), the
  strict `StartJobRequest` (`validate` | `index` | `preview` only), and
  `Job` with the six-state refinements (queued null timestamps/results;
  running start-only; terminal states require `finishedAt` + result;
  succeeded ⇔ success outcome + exit code 0; failed ⇔ non-success;
  cancelled/interrupted ⇔ terminated outcome).
- `src/readiness.ts` — the 14 fixed readiness keys, four categories,
  `ReadinessItem`, the discriminated `Observation` union (a `complete`
  observation structurally requires `evidenceId`, so a passed observation
  without evidence is unrepresentable), `ObservationSubject` (at least one
  identifier), `SiteSummary`, and `ReadinessIndex`.
- `src/client.ts` — the `ObsequiousClient` interface with the exact seven
  method signatures from docs/api.md and the readonly `mode`.
- `src/schemas.test.ts` — 31 schema tests.

### `apps/web/src/demo` (owned by this packet)

- `createDemoClient(scenario)` — validates each scenario record through
  the shared contracts at creation (malformed demo data fails loudly),
  deep-freezes results, performs no network requests, and always reports
  `mode: 'demo'`. Read methods are implemented; `saveSource`, `startJob`,
  and `getJob` reject with typed `unsupported` errors. `getSource`
  validates the path (`invalid_request` for paths outside `content/*.md`),
  rejects foreign revisions with `not_found`, and returns a real SHA-256
  `fileHash` computed via WebCrypto over the exact bytes.
- Six deterministic scenarios: `populated`, `empty`, `stale`,
  `unavailable`, `unsupported`, `request-error`. The populated fixture has
  exactly two roots, a four-level chain, a page whose source folder
  (`content/plant-care/`) differs from its parent's folder, two sibling
  pages in one folder that must not nest, all four status values, two
  source-only include dependencies, and one simulated release (documented
  in the fixture) explaining the non-null `publishedUrl`s. Readiness
  covers configured-but-not-generated, generated-but-not-deployed,
  deployed-but-not-checked, a stale pass for an older release, a current
  failure, a manual-review item, a not-applicable item, a current pass,
  and an error observation.
- `src/demo/demo.test.ts` — 23 tests.

## Contract-vs-specification check

Before building consumers, the implemented contracts were compared line by
line against docs/api.md. Findings:

- The spec's seven client method signatures, field names, and error codes
  match the implementation exactly (camelCase application fields).
- The spec does not define the *direction* of `parent` edges; the demo
  adopts "dependent → dependency" (child → parent), documented in the
  fixture, and a demo test asserts edge/parent consistency. P06 owns the
  real producer direction and must reconcile or correct this.
- "There is no passed observation without evidence" is enforced
  structurally (`complete` requires `evidenceId`), not by an extra rule.

## Acceptance evidence

- Schema tests reject malformed discriminators, invalid status
  combinations, unknown request fields (strict request schemas), a passed
  observation without evidence, current/stale/unavailable/unsupported
  state violations, job-state violations, oversized source content, and
  traversal paths (asserted in `packages/contracts/src/schemas.test.ts`).
- Current graph data requires matching source and graph revisions (test).
- All six demo scenarios satisfy the application contracts: scenario
  records are parsed through the real schemas at client creation, and the
  demo test suite constructs a client for every scenario.
- No network request, file mutation, compiler execution, or fabricated
  real verification occurs: the demo client is pure data plus WebCrypto
  hashing; `mode` is always `demo`; the request-error scenario serves no
  fallback record at all.

## Known gaps / handoff notes

- `Job`/job results are contracted and tested but no demo scenario

  design; P06 supplies the real adapter).
- The temporary `main.tsx` wiring passes a hardcoded `populated` client;

- The demo parent-edge direction is an application-side convention, not
  verified against a pinned Boris producer (P06 evidence required).
